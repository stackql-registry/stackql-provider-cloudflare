# CLAUDE.md — StackQL Cloudflare Provider, working context

This file gives a fresh Claude session everything it needs to pick up work on
this provider without re-discovering the architecture. Read this first before
making any changes.

---

## What this is

A generator that builds the **StackQL Cloudflare Provider** from two sources:

1. The upstream Cloudflare OpenAPI spec (downloaded from a Stainless-hosted
   URL; cached at `provider-dev/downloads/cloudflare-openapi.json`).
2. The Cloudflare **Python SDK** layout under `../src/cloudflare/resources/`
   (used purely as a hint for how to group operations into services).

The end product:

- **Per-service yamls** at `provider-dev/source/<service>.yaml` (intermediate
  intermediate format — useful for review and hand-editing).
- **Per-resource StackQL provider yamls** at
  `provider-dev/openapi/src/cloudflare/v00.00.00000/{provider.yaml,services/*.yaml}`
  with full `x-stackQL-resources` blocks (this is what StackQL actually loads).
- **Docusaurus markdown** at `website/docs/` for the public docs microsite.

The user has manually curated `all_services.csv` for the services
**`abuse_reports` → `alerting`** (alphabetical). From `billing.yaml` onwards,
rows were folded automatically via `fold_singletons.py`.

## Pipeline (run from the project root)

The whole chain is wrapped in a `Makefile` (run from WSL/Linux/macOS):
`make all` = specs -> mappings (strict gate: fails on unmapped operations)
-> provider (incl. all post-passes) -> meta-test (go/no-go SHOW/DESCRIBE
walk via a local server) -> docs (incl. post-passes). Individual targets:
`make specs`, `make specs-refresh`, `make mappings`, `make provider`,
`make meta-test`, `make docs`, `make smoke-test-kv` (live API, needs
CLOUDFLARE_API_TOKEN + CLOUDFLARE_ACCOUNT_ID, deliberately NOT in `all`),
`make help`. The underlying step commands:

```bash
# Step 1: download + transform upstream OpenAPI into per-service yamls
python -m stackql_cloudflare_provider.generate_specs --clean

# Step 2: write/refresh all_services.csv (preserves user edits per key)
python -m stackql_cloudflare_provider.assign_resource_names

# Step 3: generate the StackQL provider + post-pass binary wrap
npm run generate-provider

# Step 4: generate Docusaurus markdown + post-pass MDX sanitiser
npm run generate-docs
```

The `npm run generate-provider` script automatically invokes
`binary_responses.py` afterwards (wired into `bin/generate-provider.mjs`).
The `npm run generate-docs` script automatically invokes `sanitize_docs.py`
afterwards (wired into `bin/generate-docs.mjs`).

`fold_singletons.py` is a **one-shot** that has already been run — DO NOT
re-run unless we're deliberately redoing the singleton remap (and even then,
start with `--dry-run`).

## Step 1 — `generate_specs.py` pipeline detail

In order:

1. **Download** the upstream Cloudflare OpenAPI spec (URL in repo-root
   `.stats.yml`). It's JSON despite the `.yml` extension.
2. **Fanout** `/{accounts_or_zones}/{account_or_zone_id}/...` paths into
   `/accounts/{account_id}/...` and `/zones/{zone_id}/...` pairs
   (`fanout.py`). +128 paths from 64 dual-scope templates.
3. **Inline `components/parameters` $refs** into each operation's
   `parameters` list. Drop path-item-level `parameters` arrays by merging
   them down into each verb's `parameters` list (every op carries its own
   params at op level).
4. **Inline `components/responses` and `components/requestBodies` $refs**
   directly into the operation (we drop those component categories — only
   `schemas` and `securitySchemes` carry through).
5. **Rename path parameters** to snake_case (in both the path template and
   the matching `parameters[].name`). 4 renames typically (`queryId` →
   `query_id`, `livestream-session-id` → `livestream_session_id`).
6. **Rename schemas to camelCase** (with `$ref` rewrites). ~5,884 schemas
   renamed; cross-service consistency guaranteed.
7. **Flatten descriptions/summaries** to a single line (collapses `\n` to
   space) so the downstream docgen — which converts newlines to `<br />` —
   doesn't produce 80+ stray break tags per page.
8. **Normalize schemas**: `normalize.py` collapses `allOf`/`oneOf`/`anyOf`
   into a flat property-union (with `required` unioned for `allOf` and
   intersected for `oneOf`/`anyOf`). Strips `additionalProperties` and
   `discriminator`.
9. **Inline normalize** the same on inline parameter/request-body/response
   schemas (where they aren't `$ref`s).
10. **fix_required_without_properties**: drop `required` arrays where the
    sibling `properties` is missing (downstream tools assume `required[i]`
    has a matching property and crash otherwise).
11. **strip_readonly_from_write_body_required**: walk every PUT/POST/PATCH
    `requestBody.content[*].schema` and remove any `readOnly: true`
    property names from each `required:` list. Upstream Cloudflare specs
    (notably rulesets) mark response-side fields like `id`, `version`,
    `last_updated` as `readOnly: true` AND list them in the write-body's
    `required:` array. stackql's required-params dispatcher then forces
    those fields into the SET/WHERE clause, and the `naive`
    requestBodyTranslate serialises them into the JSON body — which
    Cloudflare rejects with `invalid JSON: unknown field "id"`. Handles
    both inline schemas (most cases) and `$ref`-based bodies (deep-copy +
    inline so shared response schemas aren't mutated). Typically strips
    ~100+ readOnly entries per build.
12. **Force `required: true` on every path parameter** so single-item GETs
    look different from list GETs at the planner level.
13. **Hoist inline `result.items` objects** into named component schemas
    with synthesised names like `iamPermissionsGroupResponseCollection_result_item`.
    Fixes the "no columns in Fields table" pages where `result.items` was an
    inline `{type:object, properties:{...}}` rather than a `$ref`.
14. **Normalize canonical path parameters** (`canonical_params.py`):
    rewrites every `account_id`, `zone_id`, etc. parameter to a standard
    shape `{name, in:path, required:true, schema:{type:string},
    description:"..."}`. ~3,485 rewrites per build.
15. **Assign paths to services** via:
    - exact (verb, path) SDK index match
    - static capability map (in `split.py` - 100+ entries like
      `ai` -> `ai`, `cloudforce-one` -> `cloudforce_one`, `dlp` -> `zero_trust`)
    - SDK longest-prefix (requiring >=3 segments so the bare
      `/accounts/{id}` prefix doesn't drag everything into `accounts`)
    - URL-prefix fallback through `_SERVICE_ALIASES` (e.g. `stream` ->
      `streams` to dodge the SQL reserved word).
16. **Write per-service yamls** to `provider-dev/source/<service>.yaml` -
    each is a self-contained OpenAPI 3.0 doc with only the transitively-
    referenced schemas and a snake-cased operationId on every operation
    (synthesised if upstream omitted one).

CLI flags:

- `--clean` — wipe `provider-dev/source/*.yaml` before writing.
- `--refresh` — re-download the upstream spec.
- `-s <service>` — generate only that service.
- `-v` — verbose.

## Step 2 — `assign_resource_names.py`

Walks every `provider-dev/source/*.yaml` and produces or refreshes
`provider-dev/config/all_services.csv`. The CSV has 13 columns:

```
filename,path,operationId,formatted_op_id,verb,response_object,
tags,formatted_tags,
stackql_resource_name,stackql_method_name,stackql_verb,stackql_object_key,
op_description
```

**Identity key**: `(filename, path, verb)`. On re-run, the four columns
`stackql_resource_name`, `stackql_method_name`, `stackql_verb`,
`stackql_object_key` are **preserved verbatim** if the user has edited them
(non-default value). `--reset` forces re-defaulting. `--strict` (used by
`make mappings`) exits non-zero when any operation has no existing CSV row
OR any row carries a hash-suffixed resource/method name (disambiguation
fallback) - default rows are still written so the user can curate/rename
them and re-run. The provider is hash-suffix free as of 2026-07-21.

### Verb classification (`_refine_stackql_verb`)

GET → `select` (unless response can't be projected as columns → `exec`).
GET with binary response → `select` (we wrap to a `contents` column).
PATCH → `update` (unless action verb in SDK method or path leaf → `exec`).
PUT → `replace` (unless action verb → `exec`). Keeps PATCH+PUT separate.
POST → `insert` (default — even opaque-object responses are valid inserts).
POST with action SDK method or action path leaf or `{id}` leaf → `exec`.
DELETE → `delete`.

`_ACTION_SDK_METHODS` and `_ACTION_LEAVES` are deliberately narrow lists of
true lifecycle verbs (`start`, `stop`, `cancel`, `purge`, `revoke`, etc.).
`run`, `generate`, `query`, `submit`, etc. are intentionally NOT in these
lists — they create things and should be `insert`.

### Method name (`_default_method_name`)

- Binary-response endpoints (PDF, PNG, raw text, etc.) → `<noun>_<mediatype>`
  e.g. `report_pdf`, `screenshot_png`. Verb stays `select` (we wrap to
  `contents`).
- GET ending in `{param}` → `get`. GET ending in static segment → `list`.
- Otherwise: SDK method name (snake_cased), else operationId, else
  `<verb>_<leaf>`.

### Resource name (`_default_resource_name`)

- From `x-stackql-sdk.resource_chain[-1]` if present.
- Else the last static path segment.
- Else the service name.

Then `_safe_resource_name` swaps known SQL-reserved words (`tree`, `stream`,
`release`, `full`, `analyze`) for pluralised forms (`trees`, `streams`,
`releases`, `fulls`, `analyses`). These are the empirically-confirmed
parser breakers — others (`keys`, `default`, etc.) work fine at resource
position.

### Object key (`_default_object_key`)

- List GETs: detect the array-typed envelope key (`result` preferred, then
  `items`/`data`/`records`). Skip `errors`/`messages`/`result_info`/`info`
  (envelope metadata, never the payload).
- Single-item GETs: detect the V4 envelope (`result` property + at least
  one of `success`/`errors`/`messages`/`result_info` siblings). Set
  `$.result` so stackql projects the inner payload instead of envelope
  columns.
- POST/PUT/PATCH/DELETE → no object key.

### Disambiguation pass (`_disambiguate_collisions`)

Detects `(filename, resource, method)` collisions and resolves them in
three passes:

1. **Method rename** when colliding rows have different required-param
   signatures (e.g. `/accounts/{id}/apps` vs `/zones/{id}/apps`): keep the
   resource name, rename methods to `<method>_by_<scope>` (e.g.
   `list_by_account`, `list_by_zone`).
2. **Resource rename** by prefixing parent path segments (`applications` →
   `accounts_access_applications` if needed).
3. **Hash suffix** as final fallback (rare).

A fourth pass catches signature-collision groups created by passes 1-2.

## Step 3 — provider generation

`bin/generate-provider.mjs` calls `@stackql/provider-utils.providerdev.generate`
with:

- `providerId: 'cloudflare'`
- `providerConfig: {auth: {type:'bearer', credentialsenvvar:'CLOUDFLARE_API_TOKEN'}}`
- `serviceConfig: {pagination: {requestToken:{key:'page',location:'query'},
  responseToken:{key:'result_info.page',location:'body'}}}` — Cloudflare's
  V4 page-based pagination.
- `servers: [{url: 'https://api.cloudflare.com/client/v4'}]`
- `naiveReqBodyTranslate: true` — attaches
  `config.requestBodyTranslate.algorithm = naive` to every POST/PUT/PATCH
  method that has a requestBody. Effect: callers can write
  `INSERT INTO cloudflare.accounts.accounts(name, type, unit) SELECT ...`
  instead of `INSERT INTO ... SELECT data__name, data__type, data__unit`.
  The `data__` prefix is only required when body-param names clash with
  response properties (Cloudflare's surface has no such clashes). Turn
  this off again if a future Cloudflare endpoint introduces a clash.

Output:
```
provider-dev/openapi/src/cloudflare/v00.00.00000/
├── provider.yaml          # Provider manifest with auth + service refs
└── services/<service>.yaml # Per-service spec with x-stackQL-resources
```

Then **`binary_responses.py`** runs as a post-pass. It:

1. Finds every operation with a 2xx response in a non-JSON media type
   (`application/pdf`, `image/png`, `application/octet-stream`,
   `text/plain`, the synthetic `string`, `application/scim+json`, etc.).
2. Rewrites the operation's response schema in-place to
   `{type: object, properties: {contents: {type: string}}}` under the
   original media type.
3. Attaches `response.transform` to the matching resource method:
   ```yaml
   response:
     mediaType: application/pdf
     openAPIDocKey: '200'
     overrideMediaType: application/json
     transform:
       body: '[{"contents": {{ toJson . }}}]'
       type: golang_template_text_v0.3.0
   ```

Result: users can `SELECT contents FROM cloudflare.addressing.loa_documents
WHERE account_id = '...' AND loa_document_id = '...'` and get the raw PDF
as a string column. ~38 endpoints currently wrapped across 17 services.

Then **`request_body_transforms.py`** runs as a second post-pass. It:

1. Walks every PUT/POST/PATCH op in the source yamls; for each one whose
   JSON request-body schema has at least one array- or object-typed
   property, builds a list of `(prop_name, kind)` pairs - filtering out
   readOnly properties.
2. Generates a Go template (type
   `golang_template_json_v0.3.0`) that emits a JSON body containing only
   the properties the user actually SET. Complex (array/object)
   properties use a `kindOf`-based dual-mode branch
   (`if eq (kindOf .x) "string" then .x else toJson .x end`) so both raw
   string SET literals AND parsed slice/map values serialise correctly.
   Scalar properties use plain `toJson` for proper quoting and escaping.
3. Attaches the template under `request.transform` on each matching
   resource method in the generated yamls (sibling to `config`,
   `operation`, `response`).

Why: stackql's `naive` requestBodyTranslate keeps SET values as the Go
types they were parsed as. For string-typed fields `json.Marshal`
round-trips correctly, but for array- or object-typed fields the SET
literal is kept as a Go string and gets string-wrapped on the wire
(`{"rules": "[{...}]"}`), which Cloudflare rejects with
`'rules' cannot be a string`. The transform rebuilds the body so arrays
and objects land as JSON values, not strings. ~560 methods currently
get this transform across ~80 services. Methods whose body has only
scalar properties are left alone - the naive translator handles those
correctly.

Then **`octet_stream_requests.py`** runs as a third post-pass. It
targets the handful of write endpoints whose request body is
`application/octet-stream` (KV value PUT, 5 Workers AI binary-input
models, 2 DLP dataset uploads - 8 methods total). The whole body is the
raw payload, so JSON body translation makes no sense: the pass drops
the `naive` requestBodyTranslate from those methods ONLY, injects a
`stackql`-prefixed wrapper schema (e.g. `stackqlWorkersKvValueBody`)
exposing a single required `value` column via `request.schema_override`,
and splats it verbatim onto the wire:

```yaml
request:
  mediaType: application/octet-stream
  required:
    - value
  schema_override:
    $ref: '#/components/schemas/stackqlWorkersKvValueBody'
  transform:
    type: golang_template_json_v0.1.0
    body: '{{ .value }}'
```

Because naive translation is off for these methods, callers MUST use
the `data__` prefix:

```sql
REPLACE cloudflare.kv.values
SET data__value = 'my-raw-value'
WHERE account_id = '...' AND namespace_id = '...' AND key_name = '...';
```

Then **`ai_task_families.py`** runs as a fourth post-pass. Driven by
`provider-dev/config/ai_task_families.yaml`, it collapses the ~93
per-model Workers AI run resources into 9 task-family SELECT resources
(`ai.text_generation`, `ai.text_embeddings`, `ai.text_to_image`,
`ai.speech_to_text`, `ai.text_to_speech`, `ai.text_classification`,
`ai.translation`, `ai.summarization`, `ai.reranking`), all riding the
generic `POST /accounts/{account_id}/ai/run/{model_name}` operation with
`model_name` as the discriminator (slash-containing values substitute
literally into the URL - verified live). Mechanics:

- SELECT WHERE params bind to request-body properties with UNPREFIXED
  names (`WHERE prompt = '...'`); `data__` does NOT apply to SELECT.
- The generic op's 200 response is rewritten to a typed union envelope
  (`stackqlAiRunResponseEnvelope`); object-mode families project
  `objectKey: $.result` (typed columns like `response`, `usage`, `data`,
  `shape`); contents-mode families (image/audio/array results) wrap the
  raw response as a `contents` column.
- Per-family `request.schema_override` -> `stackqlAi<Family>RunInput`
  (union of member body schemas) + a `request.transform` that
  serialises exactly the provided WHERE params.
- Member models' per-model paths and resources are DROPPED from the
  generated ai.yaml (ai went from ~123 resources to 30). The 5
  octet-stream-input models (whisper x2, resnet x2, detr) are excluded
  and keep their per-model insert resources.
- Generic `ai.run` stays as the escape hatch for unlisted models.

Example: `SELECT response FROM cloudflare.ai.text_generation WHERE
account_id = '...' AND model_name = '@cf/meta/llama-3.2-1b-instruct'
AND prompt = '...'` - each SELECT executes (and bills) an inference
call.

## Step 4 — docs generation

`bin/generate-docs.mjs` calls `@stackql/provider-utils.docgen.generateDocs`
with **`dereferenced: false`** — letting SwaggerParser do its built-in
`dereference + flattenAllOf`. This is critical: with `dereferenced: true`
the Fields tables come up empty because docgen's `getHttpRespBody` doesn't
resolve `$ref`s and just returns `{}`.

The fanout pass from Step 1 means SwaggerParser no longer chokes on the
old `{accounts_or_zones}` paths that originally forced `dereferenced: true`.

Then **`sanitize_docs.py`** runs as a post-pass. It:

1. HTML-entity-escapes `<`, `>`, `~` inside `<code>...</code>` blocks
   (Cloudflare param names like `meta.<field>[<operator>]` and
   `issue_class~neq` would otherwise be parsed as JSX/strikethrough).
2. Strips invalid `</br>` close tags. We DO NOT touch `<br/>` or `<br />`
   self-closing forms because Cloudflare puts them inside table cells where
   newlines would break the table.
3. Rewrites `](/api/resources/...)` Cloudflare-internal links to absolute
   `](https://developers.cloudflare.com/api/resources/...)` URLs.
4. Unwraps orphan `[label](#some-anchor)` links whose anchors aren't ones
   the generator actually emits (keeps `#methods`, `#parameter-*`,
   `#get*`/`#list*`/CRUD method anchors).

Then **`octet_stream_docs.py`** runs as a second post-pass. It discovers
every resource method carrying `request.mediaType:
application/octet-stream` in the generated provider yamls (attached by
`octet_stream_requests.py`, so the two passes can't drift) and rewrites
that method's SQL example on the matching docs page to show the body
column `data__`-prefixed (`SET data__value = '{{ value }}'`, or
`data__value` first in the INSERT column list). Only the matched
TabItem's sql block is touched. Idempotent.

## Key design decisions (and *why*)

### Why mirror the Python SDK hierarchy not OpenAPI tags?

Upstream tags are very granular (441 distinct). The Python SDK groups them
into 108 cohesive services that match how users think about Cloudflare.

### Why pre-normalize polymorphism in Python rather than rely on `provider-utils.normalize`?

StackQL projects schemas onto a relational model. We want tight control
over the union semantics so we can guarantee a stable, side-effect-free
superset of fields. Our normalizer runs once, in-place, so the source/
files are already flat — downstream tooling never sees polymorphism.

### Why fanout dual-scope paths instead of letting StackQL handle `{accounts_or_zones}` as a parameter?

`{accounts_or_zones}` is not a real parameter — it's literally the string
`accounts` or `zones`. Forcing users to write `WHERE accounts_or_zones =
'accounts'` is poor UX. Fanout produces two clean paths each with the
right scope ID parameter (`account_id` or `zone_id`).

### Why is `accounts.yaml` smaller now than it used to be?

A bug: my early longest-prefix matcher matched `/accounts/{account_id}`
(the bare `accounts` resource) against ANY path starting with
`/accounts/...`, dragging hundreds of paths into the `accounts` bucket.
Fixed by (a) requiring ≥3 segments for the SDK longest-prefix to count,
and (b) checking the static capability map first.

### Why use `exec` sparingly?

"exec is a last resort and only for lifecycle ops" — the user's words.
POSTs that create things (even with opaque responses) should be `insert`,
not `exec`. Only true lifecycle ops (`start`, `stop`, `purge`, etc.) and
POSTs into `{id}` paths (RPC-style "act on this specific thing") get
`exec`.

### Why fold singleton non-SELECT resources into sibling parents?

Resources with a single method that isn't `select` are usually
"verb resources" — `move`, `cancel`, `purge_cache` etc. — that semantically
belong on an existing parent (the noun being acted on). Folding them in as
`exec` methods cleans up the surface and minimises non-selectable
resources.

The user curated `abuse_reports.yaml` through `alerting.yaml` by hand;
`fold_singletons.py` was used to fold the rest (193 rows). It is now done
and need not be re-run.

### Why does `_inline_op_response_schema_refs` no longer exist?

It was a workaround for docgen running in `dereferenced: true` mode. When
I switched to `dereferenced: false` (SwaggerParser handles refs), it
became dead weight. Removed.

### Why does `bin/start-server.sh` still exist as bash?

Targets WSL/Linux/macOS. The user runs from WSL. We tried to convert to a
cross-platform Node script earlier and the user explicitly asked to
revert. Note the local stackql binary discovery order:
`$STACKQL_BIN` → `./stackql` → `stackql` on PATH → `stackql.exe` on PATH →
download. Critical default: registry path is `provider-dev/openapi`
(NOT `.../openapi/src`) — stackql appends `src/cloudflare/...` itself.

## Conventions and gotchas

### Resource / method mapping heuristics (user's rules, 2026-07-21)

When reviewing CSV mappings (new upstream ops or cleanup passes), apply
these smell tests:

- A resource prefixed with `by_` is probably a method of another
  resource accessed with a different discriminator (e.g. rulesets
  `by_tag` -> `rulesets.list_rules_by_tag_*`).
- A resource name containing a verb (`requests_new`, `events_create`,
  `relate_create`) is probably a method for the noun resource.
- Redundant doubled names (`builds_builds`) are incorrect - merge.
- Repeating the service name in a resource name is redundant
  (`workers.workers_versions` -> `workers.versions`).
- A singular resource next to a plural sibling is usually wrong -
  resources should generally be plural (`exclude` -> `excludes`,
  `subdomain` folded into `subdomains`, `integration` ->
  `integrations`).
- Hash-suffixed resources (`audit_logs_6f0256`) are pass-3
  disambiguation fallbacks - remap them as differently-named methods on
  one resource (`list_by_account`, `list_by_account_issue`,
  `list_by_zone`, ...) whose required-param signatures differ.
- Two select methods on one resource MUST have different required-param
  signatures or the meta gate fails - when they collide (e.g. workers
  `scripts-search` vs `scripts.list`, both `{account_id}`), map the
  action-flavoured one as exec instead.

### Identifier casing rules (user's mandate)

- **Schema names**: camelCase (we don't care — opaque to StackQL).
- **Service/resource/method names**: snake_case.
- **Path parameters**: snake_case (we control them).
- **Query / header / body parameters**: leave as upstream spec dictates
  (server implements them; we have to match).

### MDX gremlins to look out for

- `<` `>` `~` in `<code>` content → handled by `sanitize_docs.py`.
- `</br>` close tags → handled.
- `<br/>` self-closing inside `<td>` cells → LEAVE ALONE. Replacing with
  newlines breaks the table.
- `/api/...` Cloudflare-relative links → rewritten to absolute.
- Same-page `#anchor` links to anchors we don't emit → unwrapped.

### Description handling

Multi-line descriptions get flattened to a single line in Step 1
(`_flatten_descriptions`) because docgen's `sanitizeHtml` converts every
`\n` to `<br />`, producing walls of break tags in table cells. The
flattener converts `### Heading` markdown headers inline to `**Heading:**`
bold so the visual emphasis survives.

### When the user is editing the CSV

They open `all_services.csv` in Excel which **locks the file** on Windows.
If you see `PermissionError: [Errno 13]` when running
`assign_resource_names` or `fold_singletons`, ask them to close the CSV.

### File-state checking

Don't trust your memory about file contents. If you're about to make a
non-trivial edit, re-Read the file first — the user may have hand-edited
between turns (Excel and code edits alike).

### Running stackql to verify

The user has stackql installed at `/c/Program Files (x86)/StackQL/stackql.exe`.
On Windows MSYS/Git Bash you can run it directly. For ad-hoc DESCRIBE/
SHOW queries:

```bash
cd <project root>
echo "DESCRIBE EXTENDED cloudflare.accounts.accounts;" > /tmp/q.iql
stackql.exe --registry='{"url":"C:/.../provider-dev/openapi","localDocRoot":"C:/.../provider-dev/openapi","verifyConfig":{"nopVerify":true}}' --output csv exec -i /tmp/q.iql
```

The registry URL must use Windows-style forward-slashed paths and **must
NOT include `file://`** when invoked this way. (When run inside the bash
server script which uses `pathToFileURL`, `file:///...` works.)

### The reserved-word list

`stackql-parser` (https://github.com/stackql/stackql-parser) defines a
keywords map. We probe empirically — only `tree` and `stream` actually
break at resource/service position. Method names never reach the parser
(they're FQRN-resolved before SQL parse), so reserved method names are
fine.

## What's still open

- **Pagination is disabled.** Cloudflare V4 list responses use
  `result_info.{page, total_pages}` to signal completion, but any-sdk's
  three pagination algorithms (`token` / `offset` / `link-header`) can't
  express the "stop when `page >= total_pages`" termination. Configuring
  `responseToken.key = result_info.page` causes an infinite loop because
  page 1 keeps echoing itself. We've shipped with `serviceConfig: null`
  in `bin/generate-provider.mjs` — list endpoints return only the first
  page (default 20 rows). To re-enable: implement the proposed
  `algorithm: page_number` in any-sdk (see the issue we filed against
  `stackql/any-sdk`), then in `bin/generate-provider.mjs` set:
  ```js
  const serviceConfig = JSON.stringify({
    pagination: {
      algorithm: 'page_number',
      requestToken:       { key: 'page', location: 'query' },
      responseToken:      { key: 'result_info.page', location: 'body' },
      responseTerminator: { key: 'result_info.total_pages', location: 'body' },
    },
  });
  ```
  and regenerate. See repro and full design in the any-sdk issue.
